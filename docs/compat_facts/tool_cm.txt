按分片自动升降副本
              ●   正常降副本功能
                  –    简介：两AZ+仲裁AZ部署方式支持自动升降副本功能，修改DN的同步列表。
                  –    描述：金融、银行业对业务需要极高的容灾能力。当一个分片故障了半数及
                       以上节点，因同步备中有节点发生故障，无法执行写操作，DN执行写操作会
                       超时。为了降低对业务的影响，需要对分片上可用节点进行降副本操作，当
                       检测到故障恢复后，自动触发升副本操作。
                  –    约束条件：

                       ▪   基础保障（最多降至）：一主一备。

                       ▪   部署要求：两AZ+仲裁AZ，正常副本数大于3。

                       ▪   前提要求：DN主存在，或者DCF主存在，或者剩余的副本能选主成功。

                       ▪   升级、扩容阶段，或者ETCD不可用时，不会进行降副本操作。

                       ▪   只有半数以上DN发生故障（DN状态是down或unknown：一般为管理
                           面网络不通或进程不在；DN状态是need repair：主备断连；DN状态是
                           starting：启动中；DN状态是building：重建中），且状态持续（down
                           或unknown状态默认持续12s以上；need repair、starting和building状
                           态默认持续时间达到1min，持续时间可通过
                           replica_reduce_delay_time配置），才会自动触发降副本操作。任意节
                           点故障恢复且跟主机同步达到99%，状态持续1min（持续时间可通过
                           replica_increase_delay_time配置），就会自动触发升副本操作。只有
                           当上一轮降副本操作执行成功后，才能进行下一轮降副本操作，不支持
                           二次故障。为了防止频繁升降副本，前一次降副本升回后需等待4min才
                           能进行下一次降副本操作。

                       ▪   不支持故障跳转，比如四个副本，第一次（3, 4）故障后，（1, 2）进行
                           完降副本，第二次故障（1, 2），恢复（3, 4），此时数据库实例不可
                           用，无法选出主，且不能对（3, 4）进行降副本。

                       ▪   在升降副本结束后，才能执行switchover，且switchover只能切换到同步
                           列表中的备DN上。

                       ▪   故障节点恢复后，需要跟主机同步达到99%，才会被重新加入到主机的
                           同步列表中。

                       ▪   容备场景不开启降副本功能，dorado实例不开启降副本功能。

                       ▪   升降副本过程中，不允许切换级联备。
              ●   降副本至一主零备
                  –    简介：多副本实例支持升降副本功能，修改DN同步列表。
                  –    描述：当一个分片中的所有备机都故障后，无法执行业务。为了降低对业务
                       的影响，需要对分片上可用节点进行降副本操作，当检测到故障恢复后，自
                       动触发升副本操作。
                  –    功能开启：设置参数请参见enable_synclist_single_inst。

              CM支持的DN仲裁模式主要分为Quorum模式和DCF模式，默认模式为Quorum模式。
              ●   Quorum模式：基于多数派模式仲裁，选出同步备。
                  –    Quorum模式主要用于主备节点间的数据同步和高可用保障。在GaussDB
                       中，事务提交前需确保其对应的WAL日志成功复制到多数副本且落盘，主节

                       对外提供服务时最少存活副本数量由synchronous_standby_names决定。
                       GaussDB的Quorum模式通过多数派投票机制，在数据一致性、可用性和性
                       能之间实现平衡，适合金融、政务等高要求场景。
                       请参见主服务器和设置。

CM 支持 VIP 仲裁
              简介：VIP是虚拟IP，随主DN状态进行动态绑定和切换，即如果DN主发生了切换，原
              主DN上的虚拟IP可能动态绑定到新主DN上，用户可以只通过该IP与数据库连接，不用
              感知数据库在哪一个节点上。
              仲裁流程：

              ●   新主：
                  a.   在新主上用别名（网卡名：DN端口号）方式绑定VIP。
                  b.   把VIP添加到数据库配置项“listen_addresses”中。
              ●   原主：
                  a.   在原主上解绑VIP。
                  b.   把VIP从数据库配置项“listen_addresses”中删除。
              功能开启：在数据库实例节点上每一个cm_agent数据目录下生成cm_resource.json配
              置文件，文件中包含VIP的json字段，可通过cm_ctl工具命令生成VIP配置文件，命令请
              参见执行res命令：，可以通过cm_ctl show方法查看VIP信息。

                  说明

                  在DN选主成功后，5s内VIP绑定生效。

              约束：
              ●   只支持绑定主数据库上主DN或者流式容灾首备DN。根据bind_inst字段配置。
              ●   不支持两节点三副本以上部署。
              ●   VIP（网卡名：DN端口号）不允许被其他非虚拟IP占用，如果被占用，会被CMA
                  卸载掉，即如果配置了VIP配置文件，VIP被以（网卡名：DN端口号）绑定，如果
                  不满足绑定条件（只支持绑定主数据库上主DN或者流式容灾首备DN....），则会
                  被卸载掉。
              ●   每个节点上cm_resource.json配置文件必须一致。
              ●   只支持重启方式加载。
              ●   允许配置多个VIP，但是每个实例最多支持6个。
              ●   需要可用VIP，即需要可对外提供服务的VIP（跟现有网卡处于同一网段中）。
              ●   仅支持云上环境。
              ●   不支持在浮动ip上绑定浮动ip。

                  IP。

              ●   手动生成VIP配置文件的步骤如下：在每个节点上都需要生成相同的VIP配置文
                  件，并重启数据库实例使其生效（不建议手动操作）。请根据具体网络环境判断

              ●   线程心跳自检能力
                  –    介绍：新增自检模块，对CM实例关键线程自检。
                  –    主要流程：
                       CMA、CMS新增线程自检能力。自检线程仅依赖CPU，无任何网络或磁盘操

                       程处于hang状态，进程会自动退出，并触发仲裁（CMS重新自选主，CMA进

                       在默认参数情况下，RTO时间为3分钟，可通过修改cm_agent参数
                       thread_effective_time和cm_server参数thread_effective_time、
                       cma_fault_kill_instance_timeout优化RTO时间，参数设置太小，容易发生
                       误切换，不建议改小。
                  –    约束：
                       ETCD是仲裁的中心组件，本身具备一定的自仲裁能力，若ETCD故障、无法
                       自动恢复时，则CM不再提供服务。
              ●   磁盘检测能力
                  –    规格：

                       ▪   只检测DN、CM（CMA、CMS）的数据盘、日志盘以及DN的表空间所
                           在盘。

                       ▪   在默认参数下，读写磁盘的hang故障的RTO时间为60秒，其他操作（例
                           如open）的hang故障的RTO时间为3分钟。可通过修改cm_agent参数
                           disk_check_hung_timeout、disk_check_block_timeout优化RTO时
                           间，参数设置太小，容易发生误切换，不建议改小。
                  –    检测规则：

                       ▪   检测通过读写临时文件实现，针对文件会有四个操作：open（打开文
                           件），write（写文件），read（读文件），unlink（删除文件）。其中
                           open、write、read任意一个操作失败或者执行超时，就会判定磁盘发生
                           故障或处于hang状态，并触发仲裁。相反，unlink操作失败或执行超
                           时，则不会作为触发仲裁的条件。

                       ▪   非DIRECT读写：每隔1秒采用非DIRECT的方式向磁盘中写入1B的数据，
                           如果读写失败，通过错误码判断失败的原因，其中如果是EIO（I/O错
                           误）、EROFS（文件系统只读）、ENOSPC（磁盘空间不足）、EACCES
                           （权限不足）这些原因，会判定故障，其他类型错误暂不处理。

                       ▪   DIRECT读写：默认每隔5秒（可配）采用DIRECT的方式向磁盘中写入
                           512B（如果被检测磁盘为条带化，则写入256KB）的数据，如果写入操
                           作阻塞超过20s（如果无法判断被检测磁盘是否为条带化，则超时时间为
                           60s，写入数据的大小为256KB）没有返回，则判定磁盘处于I/O hang。
                  –    说明：

                       ▪   写入的数据大小可配置，配置的写入大小需要根据磁盘的对齐规则进行
                           对齐，如果配置时没对齐，cm会自动向上对齐。在磁盘LVM条带化场
                           景，为保障写入检测能覆盖到所有磁盘，建议写入大小根据磁盘数量和
                           数据分块大小动态调整。

                       ▪   I/O hang超时时间可配置，需要根据磁盘性能进行配置，性能差的磁
                           盘，超时时间可以适当配置长一些，进而减少业务I/O对磁盘检测的影
                           响，相应的，hang场景RTO将会变长。配置成0则关闭hang检测。

CM&DCF 联合仲裁
              DCF仲裁选主是根据Paxos协议各个节点分别发起选主，节点间相互独立，没有全局视
              角，在一些复杂的场景（例如半数节点故障自动降副本）DCF无法实现仲裁处理。联
              合仲裁的目的是借助CM的全局视角实现DCF仲裁能力增强，解决复杂场景的问题。主
              要优势包括：
              ●   一致性选主：任何故障不会发生“脑裂”双主现象。
                  在一个高可用系统中，当联系着的节点断开联系时，本来为一个整体的系统，分
                  裂成两个独立节点，两个节点开始争抢共享资源造成系统混乱、数据损坏的现
                  象，称为“脑裂”。传统模式下存在“脑裂”双主问题或新主升主后因无备机而
                  不可用等问题。CM&DCF联合仲裁模式下，DCF在选主时已经与多数派节点达成
                  一致，选主成功即意味着多数备机已认可新主，因此不会存在“脑裂”双主现
                  象。
              ●   一致性日志复制：任意节点故障、主备切换不触发数据重建。
                  传统主备切换（包括同步备节点）很容易触发日志分叉而重建数据，恢复耗时
                  久，甚至会出现选主错误，丢失数据。CM&DCF联合仲裁模式下主备切换不触发
                  数据重建。
              ●   一致性增删节点：支持升级、扩容、临时运维等场景。
                  为保证正确性，DN的增删对数据库限制较多，无法达到自动化DN移动的基础要
                  求。若对数据库不做限制则会产生复杂的异常场景，很难保证正确性。CM&DCF
                  联合仲裁模式支持动态增删DN节点，协议保证过程的一致性和正确性，支持升
                  级、扩容和临时运维等场景。

              CM&DCF联合仲裁隔离副本：

              DCF仲裁选主是根据PAXOS协议各个节点分别发起选主，节点间相互独立，没有全局
              视角。联合仲裁可以借助CM的全局视角实现DCF仲裁能力增强，解决复杂场景的问

5.11.3.2 启停数据库

启动数据库
              命令格式
              cm_ctl start [[-z AVAILABILITY_ZONE [--cm_arbitration_mode=ARBITRATION_MODE]] | [-n NODEID [-D
              DATADIR | -I RESOURCE_INSTANCE_ID]] | --server] [-t SECS]

              参数说明
              cm_ctl start可单独使用，表示启动整个数据库实例，也可以根据实际情况和中括号[]
              内参数结合使用。
              ●    -z AVAILABILITY_ZONE：启动指定AZ，AVAILABILITY_ZONE为AZ名称，可通过
                   cm_ctl query -Cvz ALL命令查询。
              ●    --cm_arbitration_mode=ARBITRATION_MODE：以多数派或者少数派模式启动
                   指定AZ。ARBITRATION_MODE共有MAJORITY、MINORITY两种模式，
                   MAJORITY为多数派模式，MINORITY为少数派模式。--cm_arbitration_mode参
                   数需要和-z参数一起使用。
              ●    -n NODEID：启动指定节点，NODEID为节点名称，可通过cm_ctl query -Cv命令

注意事项
              ●    在进行switchover操作之前，需要先确保数据库状态正常、所有业务结束，并使
                   用pg_get_senders_catchup_time视图查询无主备追赶后，再进行switchover操

              ●    -a：重置数据库主备关系为初始配置状态。

5.11.4 基于 libdaemon_client.so 的数据库组件状态查询
              自507.0版本开始，数据库管理工具新增libdaemon_client.so动态库，用于扩展数据库
              组件状态查询方式。

              客户端可通过该动态库提供的API，与本地cm_agent建立基于UNIX Domain Socket的
              进程间通信连接，获取当前节点上已部署的数据库组件运行状态，其输出信息与
              cm_ctl query -v -n <NODEID>保持一致。

规格与约束
              ●    libdaemon_client.so的使用依赖部署节点的cm_agent组件，需cm_agent组件运
                   行正常。

                  gcc -I <头文件所在目录> -L <libdaemon_client.so所在目录> -o test_daemon_client test_daemon_client.c
                  -ldaemon_client
                  执行命令如下：
                  ./test_daemon_client

              此示例使用libdaemon_client.so提供的CmInit、CmGetDbStatus、CmFreeDbStatus
              和CmUninit接口实现client的初始化和反初始化，并基于daemon_client进行组件状态
              查询。
              /*
               * test_daemon_client.c
               * 说明：test_daemon_client.c源程序，提供libdaemon_client基本功能使用示例。
              */
              #include <stdio.h>
              #include <stdlib.h>
              #include "cm_daemon_client_api.h"
              int main(void)
              {
                  int ret;
                  char *statusJson = NULL;
                  /* 1. Initialize cm daemon client */
                  ret = CmInit(1, "example_client", NULL);
                  if (ret != 0) {
                      fprintf(stderr, "CmInit failed, ret=%d\n", ret);
                      return EXIT_FAILURE;
                  }
                  printf("CmInit success.\n");
                  /* 2. Query database component status */
                  statusJson = CmGetDbStatus();
                  if (statusJson == NULL) {
                      fprintf(stderr, "CmGetDbStatus failed.\n");
                      CmUninit();
                      return EXIT_FAILURE;
                  }
                  /* 3. Use the returned JSON status */
                  printf("Database status (JSON):\n%s\n", statusJson);
                  /* 4. Free the returned status buffer */
                  if (CmFreeDbStatus(statusJson) != 0) {
                      fprintf(stderr, "CmFreeDbStatus failed.\n");
                  }
                  statusJson = NULL;
                  /* 5. Uninitialize cm daemon client */
                  CmUninit();
                  printf("CmUninit done.\n");
                  return EXIT_SUCCESS;
              }

              server.key.cipher、server.key.rand、client.key.cipher、client.key.rand。

              求，则无法使用SSL。
              chmod 400 cacert.pem
              chmod 400 server.crt
              chmod 400 server.key
              chmod 400 server.key.cipher
              chmod 400 server.key.rand
              chmod 400 client.crt
              chmod 400 client.key
              chmod 400 client.key.cipher
              chmod 400 client.key.rand

        步骤3 证书有效期的检测周期为1天，可通过ssl_cert_expire_check_interval设置。证书有效
            期剩余90天时会开始产生告警，可通过ssl_cert_expire_alert_threshold设置（配置参
            数详见ssl_cert_expire_alert_threshold)。
        步骤4 客户端和服务端的证书吊销列表分别为client.crl、server.crl。

              ----结束

6.1 日志类型简介
              在数据库运行过程中，会出现大量日志，既有保证数据库安全可靠的WAL日志（预写
              式日志，也称为Xlog），也有用于数据库日常维护的运行和操作日志等。在数据库发
              生故障时，可以参考这些日志进行问题定位和数据库恢复的操作。

日志类型
              日志类型的详细说明请参见下表。

              表 6-1 日志类型

               类型      说明

               系统日志    数据库系统进程运行时产生的日志，记录系统进程的异常信息。

               操作日志    通过客户端工具（例如gs_guc）操作数据库时产生的日志。

               审计日志    开启数据库审计功能后，将数据库用户的某些操作记录在日志中，这
                       些日志称为审计日志。

               WAL日志   又称为REDO日志，在数据库异常损坏时，可以利用WAL日志进行恢
                       复。由于WAL日志的重要性，所以需要经常备份这些日志。

               内存日志    保存数据库进程动态内存使用超过90%时的内存上下文统计信息。
